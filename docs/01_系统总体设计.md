# 01 系统总体设计

## 1.1 设计目标

| 目标 | 设计决策 |
|---|---|
| 真正的“计算机控制系统” | 控制律在 PC 上以固定采样周期 $T_s$（默认 5 ms）离散执行；采样、保持、延迟、量化都显式出现在模型和软件里，而不是被固件掩盖 |
| 教学可解释 | 所有控制器都输出同一个物理量：小车加速度 $a$ [m/s²]；增益都有物理单位与含义 |
| 仿真与实物同源 | 控制器、状态估计器、安全监督、加速度→速度指令积分器是**同一份代码**，仿真与实物只替换“对象”和“IO” |
| 安全优先 | 默认只读；运动命令必须通过协议表验证、实物标定、人工确认三道关；统一的受控减速停车 |
| 可在普通 Windows 电脑上运行 | 纯 Python（numpy/scipy/matplotlib/pyserial）；实时循环采用高精度定时 + 独立进程 |

## 1.2 控制层次

```
            ┌──────────────────────────── PC（200 Hz，本软件）──────────────────────────────┐
 电位器 ──► │ 串口解析 → 标定 θ=s(ADC−ADC₀)/k → 状态估计(KF) → 控制律 a=f(x̂) → 安全监督 → ∫a dt │──► 速度指令 v_cmd
 (ADC板)    └───────────────────────────────────────────────────────────────────────────────┘        │
                                                                                                      ▼
                                          PD42S1（驱动器内部 FOC + 速度环 + 位置环，kHz 级） ──► 步进电机 ──► 皮带 ──► 小车
                                                                   │
                                                          编码器位置（可选读回 PC）
```

- **内环**（驱动器内部）：闭环步进驱动器自身的速度/电流环，带宽远高于摆的动力学，我们把它建模为一阶滞后 $\tau_v$ 加传输延迟。
- **外环**（PC）：根据摆角、角速度、小车位置、速度计算期望加速度 $a$，积分为速度指令 $v_{cmd}$ 下发。

为什么不用驱动器的力矩模式？您截图中工作模式是“通信力矩模式”。力矩模式需要准确的电机转矩常数、同步带效率和摩擦模型；闭环步进电机在低速时的齿槽转矩也很明显。速度模式则把这些都“藏”进驱动器的内环里，小车的运动学可以精确预测（$\ddot x=a$）。对教学来说，这让模型干净且可辨识。**实物运行前需要把驱动器切换到通信速度模式**（按手册操作）。

## 1.4 实时执行模型

### 1.4.1 定时

Windows 默认计时器粒度为 15.6 ms，直接 `sleep(0.005)` 实际会睡 15 ms。`hw/timing.py`：

1. 调用 `winmm.timeBeginPeriod(1)` 把系统计时粒度提高到 1 ms；
2. 以**绝对截止时刻** $t_k=t_0+kT_s$ 调度（误差不累积）；
3. 睡到截止前 1.5 ms，再自旋等待；
4. 若严重超时，跳到下一个未来截止时刻并计数 `overruns`。

Python ≥ 3.11 在 Windows 上的 `time.sleep` 已使用高精度可等待计时器，效果更好，推荐使用 3.11+。

### 1.4.2 线程与进程

```
主进程（GUI，Tk + matplotlib）             控制进程（spawn）
  ├─ 仿真页：数字孪生（主线程）              ├─ 主线程：HardwareLoop.run()   200 Hz
  └─ 实物页：轮询 Queue 画图 ◄── Queue ──────├─ 传感器线程：逐行解析、时间戳
                           ──► Event(停止) ─►├─ 电机线程：发送最新 v_cmd、周期读位置
                                              └─ 转发线程：每 50 ms 推送日志行与状态
```

**为什么 GUI 模式要用独立进程？**这是实测结论。CPython 的线程共享一把解释器锁（GIL），matplotlib 的 Agg 渲染每次重绘都会持有它几十毫秒。在模拟实物上测得：

| 方案 | 周期中位数 | p99 | 最大值 |
|---|---|---|---|
| 控制循环为 GUI 进程内的线程 | 5.00 ms | 9.50 ms | **54.3 ms** |
| 控制循环为独立进程（本软件） | 5.00 ms | 5.32 ms | 11.5 ms |

54 ms 的偶发停顿与环路的延迟裕度（约 60 ms，见 03 章）同量级，不能接受。命令行 `run` 本身没有绘图，直接在主进程运行。

### 1.4.3 电机通信与控制循环解耦

每次串口事务（发送 + 等应答）约 1–5 ms，且偶有更长的尾部延迟。若控制循环同步等待应答，这些尾部延迟会直接变成采样抖动。所以电机通信放在单独线程：

- 控制循环只把最新的 $v_{cmd}$ 写进“邮箱”（不阻塞）；
- 电机线程取最新值发送，丢弃被覆盖的旧值（“最新优先”）；
- 每 N 个周期（默认 4）读一次编码器位置，作为小车位置测量；
- 连续失败计数交给安全监督（默认 3 次即停车）；
- 超过 50 ms 没有新指令时重发上一条（保活）。

## 1.5 运行模式与状态机

| 模式 | 读传感器 | 发运动指令 | 用途 |
|---|---|---|---|
| 仿真（GUI/`simulate`/`compare`） | 虚拟 | 虚拟 | 教学、调参、对比 |
| SIL（`sil`/GUI“模拟实物”） | 假串口 | 假串口 | 验证实时代码路径、课堂演示硬件页 |
| 影子 shadow | ✓ | ✗ | 符号检查、噪声与时序测量（绝对安全） |
| 闭环 closed | ✓ | ✓ | 实物平衡 |

实物运行状态机：

```
PREFLIGHT ──(传感器速率 ≥ 0.95/Ts，电机应答正常)──► WAIT_ARM
WAIT_ARM ──(|θ| < 3° 持续 1 s：人扶着杆)──────────► ACTIVE（此时轻轻松手）
ACTIVE ──(安全监督触发 / 停止按钮 / 空格 / Ctrl+C / 到时)──► STOPPING（v_cmd 以 a_brake 斜坡到 0）
STOPPING ──(v_cmd = 0，零速指令已确认)──────────────► DONE
任何异常 ──► 直接发送零速；若零速未被确认 → 提示“立即断开 12 V”
```

## 1.6 时序与延迟预算（设计值，需实测）

| 环节 | 估计 | 如何测 |
|---|---|---|
| ADC 采样到串口输出（固件） | 0–1 个输出周期 | 固件加 MCU 时间戳 `T=`（docs/05 第 1 步） |
| USB CDC 传输 + 驱动 | 1–3 ms | `diagnose --sensor` 的 dt 分布 |
| PC 计算 | < 0.5 ms | 日志 `dt` 列 |
| 指令串口发送 + 驱动器解析 | 1–5 ms | `probe` / `motor-step` |
| 驱动器速度环响应 $\tau_v$ | 10–20 ms（待测） | `motor-step` |
| **合计** | **约 15–30 ms** | `motor-step` + `diagnose` |

对照：开环不稳定极点 $p=5.53\,\mathrm{s^{-1}}$，经验上 $p\,\tau_{\text{总}}<0.5$，即总延迟 < 90 ms 理论可控。实际默认设计的延迟裕度约 60 ms（03 章），余量充足，但 USB 转串口芯片的“latency timer”（FTDI 默认 16 ms）会吃掉不少，务必实测。

## 1.7 设计取舍与已知局限

1. **PC 在环的非确定性**：Windows 不是实时系统，偶发停顿不可避免。对策：独立进程、日志记录每周期 `dt`、传感器数据超时即停车、延迟感知设计留出裕度。若需工业级确定性，可把同一控制律移植到 MCU，PC 只做监控和数字孪生。对比两者正是很好的课程素材。
2. **速度模式下的通信中断**：驱动器会保持最后速度，PC 侧软件无法兜底，必须加硬件限位（05 章第 0 步）。
3. **电位器死区在下垂位置旁**：平衡控制不受影响（直立点在量程中部，±165° 线性），起摆需要跨越死区，仅在仿真中提供。
4. **协议未完成**：`set_speed` 与 `read_position` 待按手册填写（07 章）。
